# 성능 측정 스크립트 (Perf 이슈에서 추가)

## 만료 회수: 타이밍 휠 vs lazy만 (#21)

레포 루트에서 돌린다(키 10만 개 기본값으로 약 4초).

```bash
python -m bench.expiry_reclaim
```

```bash
python -m bench.expiry_reclaim --keys 1000000 --seconds 120
```

[results/expiry_reclaim.csv](results/expiry_reclaim.csv)(1초마다 남은 만료 키 수)와 [results/expiry_reclaim.md](results/expiry_reclaim.md)(요약 표와 그래프)를 다시 만든다.
`python bench/expiry_reclaim.py`로 부르면 설치된 다른 체크아웃의 `mini_redis`를 읽을 수 있어서 `-m`으로 부른다.

### 무엇을 재나

키 N개를 t=0에 저장하고, 같은 키와 같은 읽기 순서(시드 21)로 두 번 돌린다.

- **휠**: 100ms마다 `Store.expire_tick()`을 부른다(만료 스레드가 하는 일과 같다).
- **lazy만**: tick을 부르지 않는다. 읽힌 키만 `_get_live`가 지운다.

두 방식 모두 핫 키 10%에만 tick마다 EXISTS 100번을 보낸다. 1초마다 tick 직전에 `store.size() - 살아 있는 키 수`, 곧 "만료됐는데 아직 메모리에 남은 키 수"를 센다.

| 시나리오 | TTL |
| --- | --- |
| spread | 1~60초에 고르게 |
| burst | 전부 10초 (tick 상한 1,000개에 걸리게) |

### 결과 (키 10만 개, 70초)

| 시나리오 | 방식 | 최대 | 평균 | 끝(70초) |
| --- | --- | ---: | ---: | ---: |
| spread | lazy만 | 91,690 | 52,803 | 90,606 |
| spread | 휠 | 196 | 144 | 0 |
| burst | lazy만 | 99,901 | 79,919 | 90,028 |
| burst | 휠 | 99,901 | 7,369 | 0 |

- **spread**: lazy만 쓰면 읽히지 않는 90%가 그대로 쌓여 70초에 90,606개가 남는다. 휠은 언제 재도 최근 100ms 안에 만료된 키(140~196개)만 남고, 마지막 만료(60초) 뒤에는 0이다.
- **burst**: 10초에 99,901개가 한꺼번에 만료된다. 휠은 tick당 1,000개 상한 때문에 1초에 1만 개씩 지워 20초에 0이 된다. lazy만은 70초에도 90,028개가 남는다.
- **tick 소요 시간**: 1,000개를 지우는 tick은 약 2ms다. 처음(#21)에는 2단 슬롯을 1단으로 내려보내는 tick이 항목마다 다시 넣느라 burst에서 락을 25~80ms 잡았다. #45에서 내려보내기를 칸째 옮기기로, overflow 이동을 tick당 1,000개로 바꾼 뒤로는 tick 최대가 spread 약 0.7ms, burst 약 2.5ms(1,000개를 지우는 tick)다.

그래프는 [results/expiry_reclaim.md](results/expiry_reclaim.md)에 있다.

### 왜 가짜 시계인가

만료 스레드는 100ms마다 `expire_tick()`을 부를 뿐이고, 무엇을 지울지는 주입한 시계 값으로 정해진다. 그래서 가짜 시계로 같은 호출 순서를 재현하면 결과가 결정적이고, 70초 측정 네 번이 몇 초면 끝난다.

실제 시간에서만 생기는 차이는 tick 자체가 걸리는 시간만큼 주기가 늘어나는 것과 스레드 스케줄링 지연이다. 실제 만료 스레드(`start_expiry`)로 2만 개 burst를 한 번 돌려 보니 만료 뒤 약 2.3초에 비워졌다. 가짜 시계 예측(2.0초)에 tick 올림(최대 100ms)과 스레드 위상을 더한 정도다.

### 한계

- 요청 스레드와 만료 스레드가 락을 두고 다투는 상황은 없다. 읽기도 같은 스레드에서 순서대로 한다.
- 휠 쪽은 tick 직전에 재므로 최근 100ms 동안 만료된 키까지 남은 것으로 센다(휠에 불리한 쪽).
- tick 상한 때문에 한꺼번에 만료되는 키가 많으면 휠도 1초에 1만 개씩만 지운다. 키 상한 100만 개가 동시에 만료되면 다 비우는 데 100초다.
- 키 수만 재고 메모리 바이트는 재지 않는다.
- TTL이 60초 안이라 overflow 힙(약 6.8분 넘는 만료)은 거치지 않는다.

## 리사이즈 지연: 일괄 리사이즈 vs 점진적 리해싱 (#24)

레포 루트에서 돌린다. 아래 결과는 첫 줄로 만들었다(키 100만 개, 방식마다 5번이라 조용한 컴퓨터에서 약 4분).

```bash
python -m bench.rehash_latency --repeat 5
```

```bash
python -m bench.rehash_latency --keys 100000 --repeat 1
```

[results/rehash_latency.md](results/rehash_latency.md)를 다시 만든다.

### 무엇을 재나

빈 `HashTable`(16칸)에 `key:0`부터 키 N개를 하나씩 넣으며 put마다 `perf_counter_ns`로 잰다.
Store는 전역 락을 잡은 채로 put을 부르므로, put 한 번이 걸린 시간이 곧 그동안 다른 요청이 기다리는 시간이다.

- **일괄 리사이즈**: `HashTable(rehash_buckets=1 << 62)`. 리사이즈를 일으킨 put이 옛 엔트리를 전부 옮긴다(main의 `_resize()`와 같은 일).
- **점진적 리해싱**: 명령마다 옛 배열 버킷을 k개씩 옮긴다. k는 1, 4(config), 16, 64를 잰다.

키 100만 개는 명세의 키 상한(`MAX_KEYS`)이다. 그 안에서 가장 큰 리사이즈는 786,433번째 put의 2^20 → 2^21칸이다.
GC는 끄고 잰다. 세대별 GC 멈춤이 두 방식에 똑같이 섞여 리사이즈 효과를 가리기 때문이다. GC를 켠 결과는 따로 한 표로 남긴다.
벽시계 값은 방식을 번갈아 여러 번 돌려 통계마다 가장 작은 값을 쓴다(timeit과 같은 이유: 리사이즈 비용은 매번 나오고, 다른 프로세스의 간섭은 시간을 더하기만 한다).
"put 하나가 옮긴 최대 엔트리"는 해시 함수 호출 수로 세어 시계와 상관없이 매번 같다.

### 결과 (키 100만 개, GC 끔, 5회 중 최솟값)

| 방식 | 버킷/명령 | put 하나가 옮긴 최대 엔트리 | p50(µs) | p99(µs) | 최대(ms) | 합계(s) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 일괄 리사이즈 | - | 786,433 | 1.5 | 2.4 | 953 | 3.47 |
| 점진적 리해싱 | 1 | 9 | 3.0 | 7.3 | 1.5 | 3.25 |
| **점진적 리해싱 (config)** | **4** | **14** | **1.9** | **10.7** | **1.7** | **3.55** |
| 점진적 리해싱 | 16 | 33 | 1.5 | 22.4 | 1.8 | 3.52 |
| 점진적 리해싱 | 64 | 83 | 1.5 | 64.2 | 0.8 | 3.51 |

- **일괄**: 리사이즈를 일으킨 put 하나가 엔트리를 전부 옮긴다. 마지막 리사이즈(786,433번째 put, 2^20 → 2^21칸)는 953ms가 걸린다. 리사이즈 구간별 최대는 12 → 25 → 52 → 107 → 232 → 463 → 953ms로 리사이즈마다 두 배가 된다. main의 `_resize()`를 그대로 불러 같은 측정을 하면 942ms로 같다.
- **점진적(4)**: put 하나가 옮기는 엔트리는 최대 14개다. 최대 1.7ms는 리사이즈를 시작하는 put이 새 배열(2^21칸, 16MB)을 만드는 시간이다. 가장 느린 put들이 정확히 리사이즈를 시작하는 put(786,433, 393,217, …)이다. 엔트리를 옮기는 비용은 p99에 보인다(2.4 → 10.7µs).
- **총시간**은 거의 같다(3.47초 vs 3.55초). 옮기는 총량은 같고 시점만 나뉜다.
- **버킷 수 고르기**: 1개면 p50이 두 배(3.0µs)다. put만 이어지면 다음 리사이즈 문턱(0.75C번)까지 옛 배열(C칸)을 다 옮기지 못해 거의 늘 두 배열을 보기 때문이다. 16개, 64개는 p99가 버킷 수만큼 커진다. 4개는 p50을 거의 지키면서 p99를 약 10µs로 둔다. HTTP 요청 한 번(수백 µs)에 비하면 작다.
- **GC를 켜면** 세대별 GC(gen2)가 엔트리 수십만 개를 훑느라 점진적 리해싱에서도 최대 196ms가 나온다(일괄은 943ms). 리사이즈를 없애면 GC가 가장 큰 멈춤이다.

리사이즈 구간별 표와 GC 표는 [results/rehash_latency.md](results/rehash_latency.md)에 있다.

### 한계

- `HashTable.put`만 잰다. HTTP와 Store의 검증, 락을 기다리는 다른 요청의 지연은 #20(락 멈춤 측정)이 잰다.
- 넣기만 한다. 실제로는 get과 delete도 버킷을 옮기므로 리해싱이 더 빨리 끝난다.
- 벽시계 값이라 다른 프로세스가 CPU를 쓰면 흔들린다. 처음 두 번은 부하가 큰 컴퓨터에서 돌아 일괄 쪽 총시간이 18초까지 늘었다. 그래서 방식을 번갈아 돌리고 최솟값을 쓰게 바꿨고, 옮긴 엔트리 수처럼 시계와 상관없는 값을 같이 둔다.

## 락 멈춤: O(N) 작업 중 다른 요청의 대기 (#20)

레포 루트에서 돌린다. 기본값(키 100만 개, 3번 반복)은 Store를 행마다 새로 채우므로 몇 분 걸린다.

```bash
python -m bench.lock_pause
python -m bench.lock_pause --keys 100000 --repeat 1 --out /tmp/lock_pause.md   # 작게, 다른 곳에
```

결과는 [results/lock_pause.md](results/lock_pause.md)에 있어요.

### 무엇을 재나

한 `Store`에 키 N개를 넣고, 다른 스레드(희생자)가 존재하는 키 하나를 계속 `get`하게 둔다.
메인 스레드가 전역 락을 잡는 O(N) 작업을 하는 구간과 겹친 희생자 호출의 지연이 "다른 요청이 락 앞에서 기다린 시간"이다.
행은 prefix 삭제, `KEYS`, 스냅샷 복사, 리사이즈(점진적과 일괄 비교)와 두 대조군이다.
대조 A는 희생자 혼자 도는 같은 길이의 구간이고, 대조 B는 락 없이 파이썬 작업만 O(N)으로 하는 구간이다. B가 GIL 하나만으로 생기는 영향을 보여 준다.
prefix 삭제 행에는 순회(스캔)만 따로 잰 시간도 함께 적는다.

### 왜 이렇게 재나

#24(`rehash_latency`)는 `HashTable.put` 하나의 시간만 쟀고, 락을 기다리는 다른 요청의 지연은 이 이슈로 넘겼다. 그래서 put 시간은 다시 재지 않고 기다리는 쪽만 본다.
리사이즈 행은 마지막 리사이즈 문턱 바로 아래까지 채운 Store에 새 키를 넣어 리해싱이 끝날 때까지 간다. 점진적 리해싱이 끝나려면 키 상한을 넘겨 put해야 해서 이 두 행의 Store는 `max_keys`를 크게 준다.
일괄 행은 `store._table`을 `HashTable(rehash_buckets=1 << 62)`로 바꿔 끼워 옛 `_resize()`를 재현한다(측정용으로만 비공개 필드를 건드린다).
리사이즈 두 행은 "GET이 같이 옮겨 주는 리해싱, 두 스레드"다. 희생자의 GET도 버킷을 옮기기 때문이다. 이 행들의 N(처음 크기)은 다른 행과 다르다(기본값에서 786,432 대 1,000,000). 마지막 리사이즈 문턱 바로 아래까지만 채워야 리사이즈가 끝날 때까지 새 키를 넣어 볼 수 있어서다. 결과에는 처음 크기, 최종 크기, 메인 스레드의 SET 수, 희생자의 GET 수를 적는다.
GC는 끄고 잰다(`--gc`로 켠다). 벽시계 값이라 행을 번갈아 반복하고, 결과 표에는 반복마다 한 줄씩 그대로 적는다. 합쳐서 만든 최솟값은 없고, 작업마다 최대 대기의 최솟값 / 중앙값 / 최댓값을 따로 요약한다. p99는 최근접 순위(`ceil(0.99·n)`번째로 작은 값)로 `cache_effect`와 같은 정의다.

### 한계

- Store 단계다. HTTP 서버의 오버헤드와 이벤트 루프는 들어 있지 않다.
- 희생자는 get 하나만 한다. 쓰기 요청이 기다리는 시간은 같은 락이라 같은 쪽으로 읽으면 된다.
- 아주 짧은 작업은 메인이 GIL을 쥔 채 끝나 겹치는 희생자 호출이 없을 수 있다. 그때는 희생자 호출 수 0, 지연 칸은 "겹친 요청 없음"으로 두고 대신 쓸 값을 만들지 않는다.
- GIL 전환 간격(5ms)은 락 대기의 상한이 아니다. 대조 B는 GIL만의 비용을 보여 주지만 락을 잡는 시간만 따로 떼어 주지는 않는다.
- 대조 A의 구간은 그 반복에서 가장 긴 작업과 같되 10초를 넘기지 않는다.
- 벽시계 값이라 다른 프로세스가 CPU를 쓰면 흔들린다.
