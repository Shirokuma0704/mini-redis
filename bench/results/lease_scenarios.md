# Lease 시나리오 측정 결과

원본 지연 200ms, lease 대기 간격(retry_after_ms) 100ms, 캐시 TTL 60초.
가짜 시계 위 이벤트 시뮬레이션이라 매번 같은 숫자가 나온다. 캐시 요청은 0ms로 친다.
`python -m bench.lease_scenarios`가 이 파일을 다시 만든다.

## 스탬피드: 인기 키가 만료되는 순간 동시 요청 100개

| 방식 | 원본 호출 | Mini Redis 요청 | 가장 늦은 응답(ms) |
| --- | ---: | ---: | ---: |
| lease 없음 | 100 | 200 | 200 |
| lease 있음 | 1 | 299 | 200 |

lease 있음의 대기자는 100ms마다 다시 묻는다. 같은 ms면 먼저 예약된 보유자의 PUT이 먼저라 여기서는
200ms에 값을 받는다. 재시도가 PUT보다 조금이라도 먼저 닿으면 한 번 더 기다려 최대 300ms다.

## Stale set: 읽는 쪽의 원본 읽기와 늦은 PUT 사이에 원본 갱신 + DEL

쓰는 쪽 시각을 읽는 쪽 GET 기준 -100ms부터 300ms까지 1ms씩 옮기며 한 번씩 돌린다.
읽는 쪽은 0ms에 원본을 읽고 200ms에 PUT한다. 칸은 끝난 뒤 캐시 상태의 실행 수다.

| 쓰는 쪽 시각 | 실행 | lease 없음: 최신 / 비어 있음 / 낡음 | lease 있음: 최신 / 비어 있음 / 낡음 | 낡음 비율 (없음 → 있음) |
| --- | ---: | ---: | ---: | ---: |
| 읽는 쪽 GET 전 (-100~-1ms) | 100 | 100 / 0 / 0 | 100 / 0 / 0 | 0.0% → 0.0% |
| 겹침: 원본 읽기 ~ 늦은 PUT (0~200ms) | 201 | 0 / 0 / 201 | 0 / 201 / 0 | 100.0% → 0.0% |
| 늦은 PUT 뒤 (201~300ms) | 100 | 0 / 100 / 0 | 0 / 100 / 0 | 0.0% → 0.0% |
| 전체 (-100~300ms) | 401 | 100 / 100 / 201 | 100 / 301 / 0 | 50.1% → 0.0% |
