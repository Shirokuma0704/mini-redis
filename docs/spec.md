# Mini Redis 기초 명세서

Nov 12, 2026 · @백찬

## 개요

Mini Redis는 해시테이블을 직접 구현한 인메모리 키-값 저장소입니다. Python + FastAPI로 만든 HTTP API로 외부에 열고, 느린 API 앞에 캐시로 붙여 성능 차이를 측정합니다.

이 명세는 세 초안(상철 초안, CLAUDE.md 초안, 백찬 명세)의 충돌을 11월 12일 결정으로 합친 통합본입니다. 코딩 규칙과 폴더 구조, 역할 분담은 CLAUDE.md를 따르되, 동작이 이 문서와 다르면 이 문서가 우선입니다.

Redis는 데이터를 RAM에 두는 키-값 저장소입니다. DB가 창고라면 Redis는 책상 서랍입니다. 메모리 접근과 O(1) 해시 조회 덕분에 빠르고, 대신 꺼지면 데이터가 사라져서 디스크 백업(스냅샷, AOF)을 둡니다.

이번 과제의 기본 사용 패턴은 cache-aside입니다.

1. 요청이 오면 먼저 Mini Redis에서 GET을 합니다.
2. 값이 있으면(hit) 바로 반환합니다.
3. 없으면(miss) 원본 API를 호출하고, 결과를 TTL과 함께 SET한 뒤 반환합니다.

## 범위

값 타입은 String 하나만 지원합니다. 단, INCR은 값을 10진 정수 문자열로 해석합니다.

**포함**

- 직접 구현한 해시테이블 위의 키-값 저장
- 키 명령: SET, GET, DEL, EXISTS, EXPIRE, TTL, INCR
- 일괄 명령: KEYS(prefix), prefix 삭제, FLUSH, 네임스페이스 무효화
- TTL 만료 (lazy + 타이밍 휠)
- Lease 토큰 (캐시 스탬피드와 stale set 방지)
- 영속성: 스냅샷 + AOF
- 단위 테스트, 기능 테스트, 캐시 유무 성능 비교

**제외**

- List, Hash, Sorted Set 등 다른 타입
- 클러스터, 복제, Pub/Sub, 트랜잭션(MULTI), 인증
- 메모리 상한 축출(eviction): 키 개수 상한만 두고, 축출은 스트레치로 둠
- Uvicorn 워커 여러 개: 프로세스마다 저장소가 갈라지므로 워커는 1개로 고정

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 기술 스택 | Python 3.11 + FastAPI, Uvicorn 워커 1개 | CLAUDE.md대로 지금 확정, 병렬 작업을 바로 시작 |
| 외부 인터페이스 | HTTP + JSON, 경로 `/keys/...` | 기능 테스트와 성능 측정이 쉽음 |

| 해시테이블 | 직접 구현, 체이닝, load factor 0.75 초과 시 일괄 2배 | 두 초안이 0.75로 일치 |
| 동시성 | 전역 락(RLock) 하나 | 단순하고 확실함, Redis의 명령 직렬 실행과 같은 효과 |
| O(N) 명령 | KEYS, prefix 삭제, FLUSH 포함 | 락 보유 시간은 키 상한 안에서 감수, FLUSH는 테이블 교체로 O(1) |
| 요청 거부 | 정상 형식의 요청도 거부할 수 있음 (lease, 버전, 용량 상한) | 상철 초안의 "거의 다 받아준다" 원칙을 대체 |
| 만료 처리 | lazy + 계층형 타이밍 휠 | 접근 없는 키도 제때 회수 |
| 시간 기준 | 벽시계 절대 시각(epoch ms), 시계는 주입 | 영속화해도 의미가 유지됨, Redis도 동일 |
| TTL | 양의 정수 초 | Redis EXPIRE와 동일 |
| 무효화 | DEL, TTL, prefix 삭제, FLUSH, 네임스페이스 버전 키 | 상황별로 골라 쓰기 |
| 스탬피드·stale set | Lease 토큰 | SET NX 락은 stale set을 못 막음 |
| 영속성 | 스냅샷 + AOF, 1초마다 fsync | 손실은 최대 약 1초, AOF가 무한히 커지지 않음 |
| 에러 형식 | `{"error":"CODE","message":"..."}` | CLAUDE.md 형식 |
| 성능 비교 원본 | 200ms 지연 가짜 API, 실제 외부 API는 시연용 | 측정을 재현할 수 있어야 함 |

## 해시테이블 설계

버킷 배열과 체이닝으로 평균 O(1) 조회를 만들고, load factor가 0.75를 넘으면 버킷을 2배로 늘립니다. 저장소 본체에는 `dict`, `set`, `collections.*`를 쓰지 않습니다.

- **엔트리**: `key`, `value`, `expire_at_ms`(없으면 무기한), `next`
- **버킷**: 엔트리 연결 리스트의 머리. 버킷 배열은 고정 길이 `list`입니다.
- **해시 함수**: FNV-1a 64비트를 직접 구현합니다. 버킷 번호는 `hash & (capacity - 1)`이고, capacity는 2의 거듭제곱(초기 16)입니다. Python 내장 `hash()`는 프로세스마다 값이 달라 쓰지 않습니다.
- **리사이즈**: `size / capacity > 0.75`이면 2배 크기 배열을 만들고 모든 엔트리를 한 번에 옮깁니다. 축소는 하지 않습니다.

| 함수 | 동작 | 복잡도 |
| --- | --- | --- |
| `get(key)` | 해시 → 버킷 → 리스트를 돌며 키 비교 | 평균 O(1), 최악 O(n) |
| `put(key, value, expire_at)` | 있으면 값과 만료 시각을 교체, 없으면 리스트 머리에 삽입하고 필요하면 `_resize()` | 평균 O(1) |
| `delete(key)` | 리스트에서 떼어내고 size를 줄임 (체인 처음·중간·끝 모두) | 평균 O(1) |
| `items()` | 모든 버킷을 돌며 엔트리를 내보냄 (KEYS, prefix 삭제, 스냅샷용) | O(capacity + n) |
| `_resize()` | 새 배열에 모든 엔트리를 재배치 | O(n), 드물게 발생 |

일괄 리사이즈는 전역 락을 잡은 채로 일어나 그 순간 모든 요청을 멈추게 합니다. 이 지연 스파이크를 성능 테스트에서 측정하고, 개선책인 점진적 리해싱은 스트레치로 둡니다.

## 외부 API 명세

모든 명령은 HTTP + JSON입니다. 키는 경로에 퍼센트 인코딩해서 넣고, `ttl`은 양의 정수 초입니다.

| 명령 | 요청 | 성공 응답 | 주요 실패 |
| --- | --- | --- | --- |
| SET | `PUT /keys/{key}` · `{"value":"...","ttl":60,"lease":"..."}` (ttl·lease 선택) | 200 `{"ok":true}` | 400, 409, 413, 507 |
| GET | `GET /keys/{key}` (`?lease=1`이면 miss 시 lease 발급) | 200 `{"value":"...","ttl":42}` | 404 (+ `lease` 또는 `retry_after_ms`) |
| DEL | `DELETE /keys/{key}` | 200 `{"deleted":true}` (없었으면 false) | — |
| EXISTS | `GET /keys/{key}/exists` | 200 `{"exists":true}` | — |
| EXPIRE | `POST /keys/{key}/expire` · `{"ttl":30}` | 200 `{"updated":true}` (없는 키면 false) | 400 |
| TTL | `GET /keys/{key}/ttl` | 200 `{"ttl":n}`, 무기한이면 -1, 없으면 -2 | — |
| INCR | `POST /keys/{key}/incr` · `{"amount":1}` | 200 `{"value":n}` | 409 `NOT_INTEGER` |
| KEYS | `GET /keys?prefix=user:` | 200 `{"keys":[...]}` (만료 키 제외) | — |
| prefix 삭제 | `DELETE /keys?prefix=user:` | 200 `{"deleted":n}` | 400 빈 prefix |
| FLUSH | `POST /admin/flush` · `{"confirm":true}` | 200 `{"ok":true}` | 400 confirm 없음 |
| 네임스페이스 무효화 | `POST /namespaces/{ns}/invalidate` | 200 `{"version":n}` | — |
| 상태 확인 | `GET /health` | 200 | — |

- **에러 형식**: `{"error":"KEY_NOT_FOUND","message":"..."}`. lease가 있으면 같은 객체에 `lease`나 `retry_after_ms`를 덧붙입니다.
- **상태코드**: 400 잘못된 입력, 404 없음·만료, 409 상태 충돌(`LEASE_INVALID`, `VERSION_MISMATCH`, `NOT_INTEGER`), 413 값 초과, 507 키 상한, 500 내부 오류. 409의 구체적인 사유는 `error` 코드로 구분합니다.
- **FLUSH 경로**: CLAUDE.md의 `DELETE /keys/all`은 "all"이라는 키의 삭제와 경로가 겹치므로 `/admin/flush`로 옮깁니다.
- **INCR**: 없는 키는 0에서 시작합니다. 기존 TTL은 유지합니다(Redis와 동일).
- **네임스페이스 사용**: 키 명령에 `?ns=user`를 붙이면 서버가 내부에서 `user:v{버전}:{key}`로 바꿔 처리합니다. ns를 붙인 GET 응답에는 현재 버전 `version`이 함께 옵니다. ns를 붙인 PUT은 lease 토큰이나 읽을 때 받은 버전(`?v=7`) 중 하나를 반드시 내야 합니다(무효화 섹션 참고).

## 만료(TTL) 처리

만료된 값은 어떤 경로로도 반환하지 않습니다(lazy). 아무도 접근하지 않는 만료 키는 타이밍 휠이 제때 지웁니다.

- **저장**: 각 엔트리가 `expire_at_ms`(벽시계 epoch ms)를 가집니다. 없으면 무기한입니다.
- **시계 주입**: `Store(clock=...)`는 epoch ms를 돌려주는 함수를 받습니다. 기본값은 `time.time()` 기반이고, 테스트는 가짜 시계를 넣습니다. CLAUDE.md의 `time.monotonic()` 규칙은 이 규칙으로 대체합니다.
- **Lazy 만료**: GET, EXISTS, TTL, INCR, KEYS가 접근할 때 `now >= expire_at_ms`이면 그 자리에서 삭제하고(AOF에는 DEL로 기록) 없는 키로 취급합니다. "만료됨"과 "원래 없음"은 구분하지 않습니다.
- **계층형 타이밍 휠**: 초기값은 다음과 같습니다.
  - 1단: 슬롯 64개 × 100ms (6.4초 범위)
  - 2단: 슬롯 64개 × 6.4초 (약 6.8분 범위)
  - 그보다 먼 만료는 overflow 목록에 두고, 상위 휠이 한 바퀴 돌 때마다 아래 단으로 내려보냅니다.
- **낡은 휠 항목 처리**: 휠 항목은 `(key, expire_at_ms)` 쌍입니다. 꺼낼 때 현재 엔트리의 만료 시각과 다르면 무시합니다. 그래서 TTL 갱신, 덮어쓰기, 삭제 때문에 휠에서 항목을 취소하는 연산이 필요 없습니다.
- **실행 위치**: 백그라운드 만료 스레드가 100ms마다 전역 락을 잡고 tick을 처리합니다. 한 tick에 최대 1,000개만 지우고 락을 놓으며, 남은 건 다음 tick으로 넘깁니다.
- **규칙**: SET에 0 이하 TTL이 오면 400, EXPIRE에 0 이하가 오면 즉시 삭제합니다. TTL 없이 SET으로 덮어쓰면 기존 TTL이 사라집니다(Redis와 동일). EXPIRE는 남은 시간에 더하지 않고, 요청한 순간부터 다시 쟽니다.

## 동시성 아키텍처

`Store`의 모든 공개 메서드는 `threading.RLock` 하나를 잡고 실행합니다. 그래서 명령 하나하나가 원자적이고, 실제 Redis의 명령 직렬 실행과 같은 효과를 냅니다.

&#91;embedded content: 전역 락 아키텍처 · 요청, 만료, 스냅샷, AOF 경로\]

- **계층**: API → `Store` → `HashTable` 순서로만 호출합니다. 락을 잡는 것은 `Store`뿐이고, 핸들러는 검증만 하고 상태를 직접 만지지 않습니다.
- **락을 같이 쓰는 스레드**: 만료 스레드(100ms마다, 최대 1,000개)와 스냅샷 스레드(복사하는 동안만)도 같은 락을 잡습니다.
- **락 밖에서 하는 일**: 디스크 I/O(AOF fsync, 스냅샷 직렬화·쓰기)는 절대 락 안에서 하지 않습니다.
- **락을 오래 잡는 명령**: 리사이즈, KEYS, prefix 삭제, 스냅샷 복사는 O(N)이라 그동안 다른 요청이 기다립니다. 키 상한(100만) 안에서 감수하고, 멈춤 시간을 성능 테스트에서 쟽니다. FLUSH는 테이블 교체라 O(1)입니다.
- **워커**: Uvicorn 워커는 1개로 고정합니다. 워커가 여러 개면 프로세스마다 저장소가 따로 생깁니다.
- **대안과 비교**: 버킷 락은 서로 다른 버킷을 동시에 처리하지만, 리사이즈와 여러 키에 걸친 명령(prefix 삭제, 스냅샷)이 어려워집니다. Python에서는 GIL 때문에 얻는 것도 적습니다.

## 무효화

무효화 수단은 다섯 가지이고, 캐시를 채우는 경로는 lease 토큰으로 낡은 값이 다시 기록되는 것을 막습니다.

| 수단 | 쓸 때 | 비용 |
| --- | --- | --- |
| DEL | 키 하나가 바뀜 (로그아웃, 원본 수정) | O(1) |
| TTL / EXPIRE | 일정 시간만 유효한 캐시·세션 | O(1) |
| prefix 삭제 | 키 묶음을 즉시 지워야 함 (메모리도 바로 회수) | O(N), 락을 그동안 잡음 |
| 네임스페이스 무효화 | 키 묶음을 즉시 무효화하되 멈춤은 없어야 함 | O(1), 옛 키는 TTL까지 메모리 차지 |
| FLUSH | 전체 초기화 (시연·테스트) | O(1), 새 테이블로 교체 |

### prefix 삭제와 FLUSH

- prefix 삭제는 `items()`로 전체를 훑으며 일치하는 키를 지웁니다. 원자성을 위해 락을 끝까지 잡으며, 키 상한(100만) 안에서의 멈춤은 감수합니다. 빈 prefix는 400입니다(전체 삭제는 FLUSH).
- FLUSH는 빈 해시테이블·타이밍 휠·lease 테이블을 새로 만들어 참조를 바꿔 끼웁니다. 옛 테이블은 가비지 컬렉터가 치웁니다. 버전 테이블은 유지합니다.
- 두 명령 모두 지운 키의 lease를 무효화합니다.

### 네임스페이스 버전 키

- 버전 테이블 `ns → version`을 둡니다(이 테이블도 직접 만든 해시테이블). 초기값은 생성 시각(ms)입니다.
- invalidate는 `version = max(version + 1, now_ms)`로 올립니다. 버전이 되돌아가 낡은 키가 되살아나는 일을 막기 위해서입니다.
- 옛 버전 키는 다시 읽히지 않고 TTL로 사라집니다. 그래서 `ns`를 붙인 SET은 TTL이 필수입니다.
- 버전 테이블은 스냅샷과 AOF에 포함해 재시작 후에도 유지합니다.

**주의: 서버 쪽 버전 변환이 여는 구멍.** 서버는 PUT이 도착한 시점의 버전으로 키를 바꿉니다. 그래서 v7에서 읽은 낡은 값이 invalidate 뒤의 v8 키에 써질 수 있습니다. ns를 붙인 PUT은 lease 토큰이나 읽을 때 받은 버전(`?v=7`) 중 하나를 반드시 내야 하며, 둘 다 없으면 400, 현재 버전과 다르면 409입니다.

### Lease 토큰

Facebook memcache(NSDI 2013) 방식입니다. 캐시 스탬피드와 stale set을 한 번에 막습니다.

1. `GET ?lease=1`이 miss를 내면 서버는 64비트 랜덤 토큰을 발급하고, lease 테이블에 `key → (token, issued_at)`을 기록한 뒤 404와 함께 토큰을 돌려줍니다.
2. 같은 키에 살아 있는 lease가 있으면, 다른 클라이언트는 토큰 대신 `retry_after_ms`를 받고 잠시 후 다시 GET합니다. 원본 API는 호출하지 않습니다.
3. 토큰을 가진 클라이언트는 원본을 호출한 뒤 PUT에 토큰을 실어 보냅니다. 토큰이 일치하면 저장하고 lease를 지웁니다.
4. 그 사이 해당 키가 DEL, prefix 삭제, FLUSH로 지워지면 lease를 무효화합니다. 늦게 온 PUT은 409로 거부됩니다.
5. lease는 10초 뒤 자동으로 만료됩니다. 토큰 보유자가 죽어도 다음 요청이 새 lease를 받습니다.

- lease는 버전이 붙은 실제 키에 묶입니다. 네임스페이스를 invalidate하면 키 자체가 바뀌므로 진행 중이던 lease의 PUT도 409가 됩니다.
- lease는 일회성 상태라 스냅샷에도 AOF에도 넣지 않습니다.
- ns가 없는 키에 한해, 토큰 없는 PUT은 일반 쓰기로 허용합니다.

## 영속성 (스냅샷 + AOF)

쓰기 명령은 AOF에 덧붙이고 1초마다 fsync합니다. 주기적으로 스냅샷을 뜬 뒤 AOF를 비웁니다. 서버가 죽어도 잃는 데이터는 최대 약 1초치이고, AOF는 무한히 커지지 않습니다.

### AOF

- **기록하는 것**: SET, DEL, EXPIRE, INCR(결과값을 SET으로), prefix 삭제(지운 키마다 DEL로), FLUSH, 만료로 인한 삭제(DEL로), 네임스페이스 버전 변경
- **기록하지 않는 것**: GET, KEYS 같은 읽기, lease
- **형식**: 한 줄에 JSON 하나입니다. 예: `{"op":"set","k":"user:v3:42","v":"...","exp":1762934400000}`. TTL은 상대값이 아니라 절대 만료 시각으로 기록합니다. INCR을 결과값 SET으로 남기는 것도 재생할 때 같은 결과를 내기 위해서입니다.
- **쓰기 경로**: 명령은 전역 락 안에서 메모리 버퍼에 줄을 추가하기만 하고 바로 응답합니다. 별도 스레드가 1초마다 버퍼를 바꿔 끼우고 파일에 쓴 뒤 fsync합니다. 디스크 I/O는 락 밖에서 일어납니다. CLAUDE.md의 "AOF 기록 후 응답"은 이 규칙으로 대체합니다.

### 스냅샷

초기값은 5분마다, 또는 AOF가 10MB를 넘으면 스냅샷을 뜹니다.

1. 락을 잡고 모든 엔트리(키, 값, 만료 시각)와 버전 테이블을 리스트로 복사합니다. 같은 순간 AOF를 새 파일로 전환하고 락을 놓습니다.
2. 락 밖에서 복사본을 임시 파일에 쓰고 fsync한 뒤, rename으로 스냅샷 파일을 원자적으로 교체합니다.
3. 교체가 끝나면 스냅샷 이전의 AOF 파일을 지웁니다. 중간에 죽으면 이전 스냅샷과 이전 AOF가 남아 있어 그대로 복구됩니다.

1번의 복사는 O(N)이라 그동안 모든 요청이 멈춥니다. 직렬화와 디스크 쓰기를 락 밖으로 빼서 멈춤을 복사 시간으로 줄이고, 이 시간을 성능 테스트에서 쟽니다.

### 복구

기동할 때 스냅샷을 읽고, 그 뒤의 AOF를 순서대로 재생합니다. 만료 시각이 이미 지난 항목은 건너뛰고, 끝이 잘린 마지막 줄은 버립니다. 복구가 끝난 뒤에 만료 스레드와 서버를 시작합니다.

## 제약과 엣지 케이스

키는 1\~256바이트(UTF-8), 값은 1MB 이하, 키 개수는 100만 개 이하입니다. 아래 상황은 모두 테스트 케이스가 됩니다.

| 상황 | 처리 |
| --- | --- |
| 빈 키, 256바이트 초과 키 | 400 `INVALID_KEY` |
| 키에 `/`, 공백, 한글 | 퍼센트 인코딩, 디코딩 후 길이 검사 |
| 값 1MB 초과 | 413 `VALUE_TOO_LARGE` |
| 빈 문자열 값 | 허용, 조회 시 `""` (없음과 구분) |
| TTL이 정수가 아님 (1.5, "abc") | 400 `INVALID_TTL` |
| SET에 0 이하 TTL | 400 `INVALID_TTL` |
| EXPIRE에 0 이하 TTL | 즉시 삭제 |
| 없는 키에 EXPIRE, DEL | `false` (에러 아님, 키가 새로 생기지 않음) |
| TTL 없이 SET으로 덮어쓰기 | 기존 TTL 제거 |
| 만료 직후 GET | 404, 원래 없던 키와 구분하지 않음 |
| 만료 후 같은 키 재저장 | 새 키로 저장, 낡은 휠 항목은 무시됨 |
| 정수가 아닌 값에 INCR | 409 `NOT_INTEGER` |
| 없는 키에 INCR | 0에서 시작해 결과 1 |
| 여러 스레드 동시 INCR | 최종값 = 횟수 합 |
| 같은 키에 동시 PUT | 락을 잡은 순서대로 처리, 최종값은 보낸 값 중 하나 |
| 빈 prefix로 삭제 | 400 `EMPTY_PREFIX` |
| confirm 없는 FLUSH | 400 `CONFIRM_REQUIRED` |
| `ns`를 붙인 SET에 TTL 없음 | 400 `TTL_REQUIRED` |
| `ns`를 붙인 SET에 lease도 버전도 없음 | 400 `GUARD_REQUIRED` |
| `ns`를 붙인 SET의 버전이 현재와 다름 | 409 `VERSION_MISMATCH` |
| 무효화되거나 만료된 lease로 PUT | 409 `LEASE_INVALID` |
| 키 개수 상한 초과 쓰기 | 507 `CAPACITY_EXCEEDED` |
| AOF 마지막 줄이 잘림 | 그 줄만 버리고 기동 |
| 스냅샷 도중 죽음 | 이전 스냅샷 + 이전 AOF로 복구 |
| 서버 재시작 | 만료된 키는 복구하지 않음, 버전 테이블은 유지 |
| 시스템 시계가 뒤로 감 | 만료가 늦어지거나 일찍 일어남 (알려진 한계) |

## 테스트와 성능 비교

pytest 단위 테스트로 저장·조회·삭제를 검증합니다. 그다음 200ms 지연을 넣은 가짜 원본 API 앞에 Mini Redis를 붙여 기능과 성능을 측정합니다. 실제 외부 API(날씨·환율)는 응답 시간이 들쓭날쓭해 측정에는 쓰지 않고 시연에만 씁니다.

### 단위 테스트

시간을 다루는 테스트는 sleep 대신 가짜 시계를 씁니다. 이름은 `test_<대상>_<상황>_<기대결과>`입니다.

- [ ] 해시테이블: 충돌 강제(같은 버킷), 체인 처음·중간·끝 삭제, 리사이즈 전후 전체 조회
- [ ] TTL: 만료 직전·직후 GET, 덮어쓰기로 TTL 제거, EXPIRE가 남은 시간에 더하지 않음, EXPIRE 0 이하
- [ ] 타이밍 휠: 낡은 항목 무시, 단 간 내려보내기, tick당 삭제 상한
- [ ] INCR: 없는 키, 정수 아닌 값, TTL 유지, 스레드 10개 × 1,000회 동시 INCR
- [ ] 일괄 명령: KEYS가 만료 키 제외, prefix 삭제 개수, FLUSH 후 빈 상태와 버전 유지
- [ ] Lease: 발급·대기·PUT 성공, DEL·prefix 삭제·FLUSH 후 PUT 409, 10초 후 재발급
- [ ] 네임스페이스: invalidate 후 이전 값 안 보임, invalidate 사이에 끼인 느린 PUT 409, 재시작 후 버전 유지
- [ ] 영속성: 스냅샷 + AOF로 복원, 만료 항목 건너뛰기, 잘린 마지막 줄, 스냅샷 도중 죽음

### 기능 테스트와 성능 비교

샘플 앱이 cache-aside로 Mini Redis를 쓰는 구성에서 실제 HTTP로 측정합니다. 세션 장면(로그인 → 활동 시 EXPIRE → 로그아웃 시 DEL → 조회 404)도 기능 테스트에 넣습니다.

| 시나리오 | 비교 | 측정 |
| --- | --- | --- |
| 캐시 효과 | 캐시 없음 vs 있음 (첫 요청과 이후 요청 분리) | p50·p95 지연(ms), 초당 처리량, hit ratio |
| 스탬피드 | 인기 키 만료 순간 동시 100요청, lease 없음 vs 있음 | 원본 API 호출 수 |
| Stale set | DEL과 늦은 PUT을 경합시킴, lease 없음 vs 있음 | 최종 캐시 값이 최신인가 |
| 락 멈춤 | 키 100만 개에서 리사이즈, prefix 삭제, 스냅샷 복사 | 그동안 다른 요청의 최대 지연 |
| 만료 회수 | 타이밍 휠 vs lazy만 | 시간에 따른 남은 만료 키 수 |

## 알려진 한계와 스트레치

한계는 발표에서 먼저 밝힐 항목이고, 스트레치는 시간이 남을 때 위에서부터 합니다.

**알려진 한계**

- 전역 락을 잡은 O(N) 작업(리사이즈, prefix 삭제, KEYS, 스냅샷 복사) 동안 모든 요청이 멈춥니다.
- 명령 실행이 한 번에 하나라 코어를 여러 개 쓰지 못합니다. Python GIL과 Uvicorn 워커 1개 제약도 같은 방향입니다.
- 서버가 죽으면 최대 약 1초치 쓰기를 잃습니다.
- 시스템 시계가 바뀌면 만료가 틀어집니다. 영속화를 위해 벽시계를 택한 대가입니다.
- 무효화된 옛 버전 키는 TTL이 끝날 때까지 메모리를 차지합니다.

**스트레치 (우선순위 순)**

1. XFetch 확률적 조기 갱신: lease 발급에서 PUT까지 걸린 시간으로 서버가 재계산 시간(delta)을 자동 측정
2. 점진적 리해싱: 테이블 두 개를 두고 명령마다 버킷 몇 개씩 옮김(Redis 방식)
3. SIEVE 축출(NSDI '24): 키 상한에서 쓰기를 거부하는 대신 내보냄
4. prefix 삭제를 배치로 나눠 락을 중간중간 놓기 (원자성을 포기하는 대신 멈춤 감소)
5. 전역 락 vs 버킷 락 처리량 비교
